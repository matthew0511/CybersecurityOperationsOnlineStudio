### First-time owner access

1. Open the live HTTPS workspace above.
2. In your AWS account, use Secrets Manager in **Ohio (`us-east-2`)** to retrieve the value of **`cyber-ops-online-studio-dev/setup`**. Do not put that value in source control, chat, or support tickets.
3. Expand **First-time owner setup**, enter the code, choose your username, and set a password of at least 16 characters. Setup stops working once the owner exists.
4. Sign in, create your organization, and begin recording your program. No customer records or desktop vault data were migrated automatically.

There are no default credentials. The validation owner was temporary and removed after acceptance testing. Its synthetic organization is archived; immutable synthetic audit history is retained.

### Default third-party risk questionnaire

Assessments includes a **New third-party questionnaire** option containing all 60 owner-supplied questions with multiline responses and saved-response progress. It is also selectable in Create Assessment → Template Id. [Instructions and response semantics](docs/THIRD_PARTY_QUESTIONNAIRE.md). Existing assessments are unchanged.

### Interface refresh

The Studio now includes executive charts, grouped navigation, searchable and configurable tables, guided forms, record detail panels, framework progress cards, and branded PDF/Excel reports. [Changes and validation](docs/UI_REFRESH.md).

### Online capabilities

The browser workspace provides assessments and templates, risk/remediation and residual scores, framework activation and scoped implementation tracking, reference control evaluations, vendors, vulnerabilities, evidence upload/review, change management and CAB records, audits/findings, initiatives, board records, CSV preview/import, executive/board PDF and Excel reports, and domain audit history. An advanced action form exposes the supported public service operations.

This release is **single-owner**, with access to all organizations in the installation. It does not implement multiuser RBAC, MFA/SSO, automated scanners, complete licensed framework catalogs, incident/BCDR automation, or compliance certification. Policies and incidents retain the original source version's imported-inventory behavior. Existing operator-entered reviewer names are not authenticated signatures. Independent security/privacy review and restore testing remain outstanding before sensitive production use.

## Features

| Module | Implemented functionality | Critical limitation |
| --- | --- | --- |
| Local vault | AES-256-GCM encrypted serialized SQLite, Argon2id key derivation, atomic writes, backups | Not SQLCipher; full in-memory serialization, unencrypted PDF/XLSX exports |
| Organizations | Many client workspaces within one vault, organization-scoped read/write validation | No independent per-client user accounts or cloud multiuser access |
| Assessments | Versioned custom templates; 8 synthetic baseline questions; basic questionnaire | No official certified questionnaire or control outcome coverage |
| Frameworks | NIST CSF 2.0 category IDs/headings, CIS Controls v8.1 top-level headings | No full NIST outcomes or licensed CIS safeguard texts |
| Risk and remediation | Inherent and residual scores, acceptance history, expiration, action tracking | Approver name is operator-attested, not independently authenticated |
| Evidence | Files ≤ 5 MiB, hash verification, evidence review, optional expiration and linked control tests | Review is manual; no independent artifact validation |
| Control evaluations | Per-organization assessment of framework headings, append-only versions, evidence-aware counts | Not proof of framework compliance; no safeguard/subcategory-level assessments |
| Vendors | Register, criticality, data access, BAA applicability, review history, renewal due | BAA is manually classified; no legal evaluation |
| Vulnerabilities | Manual findings, CVSS user input, severity, asset label, due date, status history | No scanner or CVE feed integration |
| Notion migration | Risk Register plus Compliance Tracker, Security Policies, Vendor Assessments, Incident Tracker CSV; dry-run and atomic import | No API sync, relationship reconstruction, bulk ZIP importer, or historical approval trust |
| Executive reports | PDF and multi-tab Excel snapshot with risk, control, evidence, vendor, vulnerability and imported data | Not certified compliance scores; plaintext reports must be protected |
| Approvals | Re-enter vault passphrase when recording an acceptance decision | Verifies current vault operator only; not identity/authorization of named approver |

## Setup on Windows

1. Install **64-bit Python 3.12** from [python.org](https://www.python.org/), choosing the Python Launcher during setup. Extract this archive to a local non-synced directory.
2. Open PowerShell within the extracted folder and run:

   ```powershell
   py -3.12 -m venv .venv
   .\.venv\Scripts\python.exe -m pip install --upgrade pip
   .\.venv\Scripts\python.exe -m pip install -e '.[dev]'
   .\.venv\Scripts\python.exe -m pytest -q
   .\.venv\Scripts\python.exe -m cyberstudio
   ```

3. Alternatively, double-click `scripts/start_windows.bat`; it creates a virtual environment on first run, downloads dependencies, and launches the application. An internet connection is required for initial dependency installation, not for normal offline use.
4. Create or unlock a local vault with a passphrase of at least 12 characters. No recovery service exists. Store an encrypted backup and passphrase securely.
5. Create an organization and complete the synthetic exercise before using any business data.
6. In **Frameworks**, select NIST CSF or CIS Controls metadata; in **Controls**, record implementation/test results and optional linked evidence. No source metadata implies success.
7. In **Vendors**, add suppliers and record dated reviews. In **Vulnerabilities**, enter findings and track status and due dates.
8. In **Evidence**, upload/review artifacts and optionally set an expiration date. Effective status changes to expired in reports when the date passes.
9. In **Notion Import**, choose a source type and select an individual CSV from the exported Notion ZIP, inspect the preview, then confirm. Do not select the ZIP directly or mistake imported source statuses for approvals.
10. In **Reports**, export executive PDF or Excel snapshots. These are unencrypted plaintext files.

## Migrating from Phase 2

1. Back up the Phase 2 `.csvault` using Phase 2 **Settings**, then close the Phase 2 app.
2. Keep that verified encrypted backup outside the application directory. Protect its passphrase.
3. Launch Phase 3 with the same OS user account and vault path. The upgrade is additive: the existing evidence table gains `expires_on`; new v3 tables are created; `PRAGMA user_version` becomes `3`.
4. Verify existing organizations, questionnaire responses, risks, attachments, exports, acceptance dates, and audit history.
5. Do not reopen a v3 vault using Phase 1/2 binaries. Forward compatibility is not guaranteed. If a migration fails, restore the original backup only after closing the app.

The default vault is stored in the OS user data folder from `platformdirs`, usually under the Windows profile, not alongside the source ZIP. A malicious device administrator, malware, unlocked session, system swap file, or plaintext export may still expose information.

## Design and safety notes

The app is designed for one local operator. It scopes records by organization, but does not provide cryptographically separate organizational vaults, multiuser identity, RBAC, SSO, background scheduling, automatic vulnerability scanning, or independently verified sign-offs.

Imported vendor data and policies are deliberately normalized to unverified; original source claims are preserved in separate notes for review where supported. Framework mappings are topic associations only.

Treat this as a working prototype to iterate and verify, not a compliance attestation or suitable clinical data repository.

**Authoritative implementation details:** `docs/PHASE3_IMPLEMENTATION_SPEC.md` and code under `src/`. Older phase-specific documents are retained for history and may describe functionality that was incomplete when written.
